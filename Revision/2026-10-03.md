## `interesection-two-sorted-arr`

### What it’s asking

You’re given two arrays already sorted in non-decreasing order. Return a new array containing their **intersection** — values that appear in **both**.

Because inputs can contain duplicates, ask: *with what multiplicity?* The intended solve emits once each time the two pointers agree, then advances **both**. So each value appears **`min(count_in_nums1, count_in_nums2)`** times — multiset / “Intersection of Two Arrays II” behavior on sorted inputs — **not** distinct-only set intersection.

Example from your `input.txt`:  
`[1, 2, 2, 3, 3, 3]` ∩ `[2, 3, 3, 4, 5, 7]` → `[2, 3, 3]`  
(one `2` because `nums2` has only one; two `3`s because both sides have ≥2).

### Tip-offs / how you’d recognize this

- Both inputs are **sorted** (or you’re allowed / expected to sort first).
- Words like **intersection**, “common elements,” “present in both.”
- Output should stay sorted (falls out of the merge walk).
- Linear `O(n + m)` expected if you exploit sortedness — hashing works too but doesn’t need sorted input.
- Contrast tip-offs:
  - **Union** → emit when in *either* array (your earlier solve).
  - **Distinct intersection** → emit each common value only once (extra skip / set).
  - **Unsorted + frequencies** → frequency map is often cleaner.

### Pattern name(s) + why they fit

**Primary: two-pointer merge walk on sorted arrays (intersection variant).**  
Same family as merge-sort’s merge and as `union-two-sorted-arr`. One index on each array; always advance the side with the smaller head (that value can never match anything still ahead on the other side). On equality, you’ve found a shared occurrence — record it and advance **both**.

**Why not a hash set?**  
Fine for *distinct* intersection on unsorted data. Multiset needs a frequency map. Sorted two-pointers give `O(1)` extra space (besides output) and make the “why advance this side?” reasoning interview-friendly.

**Relationship to union (same family, opposite emit rule):**

| Situation | Union (earlier solve) | Intersection (today) |
|-----------|------------------------|----------------------|
| `a < b` | emit `a`, advance `i` | emit nothing, advance `i` |
| `a > b` | emit `b`, advance `j` | emit nothing, advance `j` |
| `a == b` | emit once, advance both | emit once, advance both |
| Drain leftovers | yes — leftovers are in the union | **no** — leftovers can’t be in both |

### Approach skeleton

1. Init `i = 0`, `j = 0`, empty `result`.
2. While `i < len(nums1)` **and** `j < len(nums2)`:
   - If `nums1[i] == nums2[j]`: append that value; `i += 1`; `j += 1`.
   - Else if `nums1[i] < nums2[j]`: this `nums1` value can never match a future `nums2[j]` → `i += 1`.
   - Else: symmetrically `j += 1`.
3. Stop when either pointer runs out. **Do not** drain the remainder.
4. Return `result`.

Optional polish: for **distinct** intersection only, after a match skip all duplicates of that value on both sides (or guard with `if not result or result[-1] != val` before append).

### Concrete example — state table

**Case A** (from your input):  
`nums1 = [1, 2, 2, 3, 3, 3]`, `nums2 = [2, 3, 3, 4, 5, 7]`

| Step | `i` | `j` | Heads | Rule | Action | `result` |
|------|-----|-----|-------|------|--------|----------|
| 0 | 0 | 0 | (1, 2) | 1 < 2 | advance `i` | [] |
| 1 | 1 | 0 | (2, 2) | equal | append 2; advance both | [2] |
| 2 | 2 | 1 | (2, 3) | 2 < 3 | advance `i` | [2] |
| 3 | 3 | 1 | (3, 3) | equal | append 3; advance both | [2, 3] |
| 4 | 4 | 2 | (3, 3) | equal | append 3; advance both | [2, 3, 3] |
| 5 | 5 | 3 | (3, 4) | 3 < 4 | advance `i` | [2, 3, 3] |
| 6 | 6 | 3 | — | `i` exhausted | **stop** (no drain) | **[2, 3, 3]** |

The second `2` in `nums1` never finds a partner — multiplicity is capped by the scarcer side.

**Case B:**  
`nums1 = [1, 2, 2, 3, 5]`, `nums2 = [1, 2, 7]` → **`[1, 2]`**  
(equal→1, equal→2, then `2/3/5 < 7` advance `i` until done; never emit `7`; never drain).

### Common pitfalls / edge cases

1. **Draining leftovers like union** — wrong; leftovers are exclusive to one array.
2. **Multiset vs distinct** — clarify with the interviewer. Your solve is multiset (`min` of frequencies).
3. **Advancing only one pointer on equality** — can double-count or miss pairs; equality advances **both**.
4. **Assuming no duplicates** — your tests include repeats; the algorithm must handle them.
5. **Empty array** — one empty input ⇒ empty intersection (while never runs).
6. **Unsorted input** — pointer logic is wrong unless you sort first.
7. **Repo hygiene (non-pattern):** folder typo `interesection-…`; empty `expected.txt` — fix when you tidy.

### Complexity

- **Time:** `O(n + m)` — each index moves at most once.  
- **Space:** `O(1)` extra besides the output (size ≤ `min(n, m)`).

If you sorted unsorted inputs first: dominated by `O(n log n + m log m)`.

### Quiz cards

**Front 1 — Recognition**  
Cold prompt: “Both arrays are sorted. Return every value that appears in both; if 5 appears twice in each, 5 should appear twice in the answer.” What pattern, and what do you do on `a < b` vs `a == b`?

**Back 1**  
Two-pointer sorted intersection (multiset). On `a < b`, advance the smaller side only (no emit). On `a == b`, emit once and advance **both**. Never drain leftovers.

---

**Front 2 — Gotcha vs union**  
Someone pastes your sorted **union** code, deletes appends on the `<` / `>` branches, but keeps the final “drain both leftovers” loops. What’s still wrong?

**Back 2**  
The drain loops. Intersection must **not** append remaining elements — those were never matched. Equality still advances both and emits once (union had that part right).

---

**Front 3 — Transfer / variant**  
Variant A: “Return distinct common values only.” Variant B: “Arrays are unsorted; still need multiset intersection.” How does the approach change for each?

**Back 3**  
A: Stay on two pointers; after emitting `x`, skip consecutive duplicates of `x` on both sides (or refuse to append if `result[-1] == x`).  
B: Sort + two pointers, **or** frequency map on the smaller array and scan the other while decrementing counts — hash no longer needs sortedness; two-pointers alone on unsorted data is wrong.

## Pattern cheat map (today)

| Pattern | Tip-off | Problem | Complexity | Cousin |
|--------|---------|---------|------------|--------|
| Two-pointer merge walk — **intersection** | Two sorted arrays; common elements; optionally with multiplicity | `interesection-two-sorted-arr` | O(n+m) / O(1) extra | `union-two-sorted-arr` (same walk, opposite emit + drain) |

### Mini decision tree — sorted pair problems

```
Two sorted arrays, need a combined answer?
├─ Values in EITHER  → Union      (emit on <, >, ==; drain leftovers)
├─ Values in BOTH    → Intersection
│   ├─ with multiplicity → emit on == only; advance both; NO drain
│   └─ distinct only     → same, plus skip duplicate runs after emit
└─ Need "are they disjoint / one a subset?" → same walk, boolean state
```

### Narrate this in interviews

> “Sorted + two arrays → two pointers. Union emits on inequality; intersection only on equality; leftovers matter only for union.”

That one sentence unlocks merge-interval cousins and later “intersection of k sorted lists” (k-pointer / heap).
