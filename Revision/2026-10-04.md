## 1. `leaders-in-an-array`

### What it’s asking

Return every **leader**: an element that is **strictly greater than every element to its right**. The rightmost element is always a leader. Emit leaders in the **same left-to-right order** they appear in `nums`.

Example from your `input.txt`:  
`[1, 2, 5, 3, 1, 2]` → `[5, 3, 2]`  
(`2` is always a leader as the last element; `3` beats `[1,2]`; `5` beats `[3,1,2]`; nothing left of `5` qualifies.)

### Tip-offs / how you’d recognize this

- “Greater than **all** to the right” / “leaders” / “survives a rightward scan.”
- Rightmost element is a free answer — suggests thinking from the **right**.
- Output order must match original order (not reverse of discovery).
- Contrast tip-offs:
  - “Next greater element” → stack / monotonic structure (different family).
  - “Local maxima vs neighbors” → only adjacent check, not full suffix.

### Pattern name(s) + why

**Right-to-left scan with a running maximum (suffix max).**  
A leader is exactly “strictly greater than the max of its right suffix.” Walking left from the end, maintain `max_right`. Whenever `nums[i] > max_right`, you’ve found a leader and update `max_right`.

Discovering right→left naturally builds leaders in reverse; reverse once (or prepend carefully) to restore left→right order.

### Approach skeleton

1. If empty, return `[]`.
2. Start at the last index: `max_right = nums[n−1]`, `result = [max_right]`.
3. For `i` from `n−2` down to `0`:
   - If `nums[i] > max_right`: append to `result`, set `max_right = nums[i]`.
4. Reverse `result` (or build with a deque/prepend) so order matches the array.
5. Return `result`.

### Concrete example (state changing)

Input: `nums = [1, 2, 5, 3, 1, 2]`, `n = 6`

| Step | `i` | `nums[i]` | `max_right` before | Leader? | `result` (discovery order) | `max_right` after |
|------|-----|-----------|--------------------|---------|----------------------------|-------------------|
| init | 5 | 2 | — | yes (always) | `[2]` | 2 |
| 1 | 4 | 1 | 2 | no (`1 ≯ 2`) | `[2]` | 2 |
| 2 | 3 | 3 | 2 | **yes** | `[2, 3]` | 3 |
| 3 | 2 | 5 | 3 | **yes** | `[2, 3, 5]` | 5 |
| 4 | 1 | 2 | 5 | no | `[2, 3, 5]` | 5 |
| 5 | 0 | 1 | 5 | no | `[2, 3, 5]` | 5 |

Reverse → **`[5, 3, 2]`**.

### Common pitfalls / edge cases

1. **Using `≥` instead of `>`** — ties to the right kill leadership when the problem wants *strictly* greater.
2. **Forgetting to reverse** — returning discovery order is reverse of required order.
3. **Left-to-right nested scan** — O(n²) works but interviews expect the O(n) suffix-max idea.
4. **Single-element array** → `[nums[0]]` only.
5. **Strictly decreasing array** → every element is a leader; strictly increasing → only the last.

### Complexity

- **Time:** O(n)  
- **Space:** O(k) for k leaders (output); O(1) extra beyond that if you reverse in place on a list you built

### Quiz cards

**Front 1:** Why does a right-to-left scan beat a left-to-right “check all to the right” loop?  
**Back 1:** Left-to-right naively rechecks each suffix → O(n²). Right-to-left compresses “all to the right” into one running max → O(n).

**Front 2:** Walk `[4, 4, 4]`. Who are the leaders, and why?  
**Back 2:** Only the last `4`. Earlier equals are *not* strictly greater than the suffix max.

**Front 3 (variant):** “Return leaders in *decreasing* order of value.” What changes?  
**Back 3:** Discovery order (right→left) already emits decreasing values when each new leader beats `max_right`. Skip the final reverse — or sort if you built left→right.

## 2. `majority-element-i`

### What it’s asking

Find the element that appears **more than `n/2` times**. The array is **guaranteed** to have one. Example: `[7, 0, 0, 1, 7, 7, 2, 7, 7]` → `7` (5 of 9).

### Tip-offs / how you’d recognize this

- “Majority” / “appears more than n/2” / “guaranteed to exist.”
- You need the *value*, not a full frequency map (though a map works).
- O(1) extra space is a common follow-up → voting / cancelation idea.
- Contrast tip-offs:
  - “More than n/3” → Boyer–Moore generalized to **two** candidates.
  - “No guarantee” → after voting, **verify** with a count pass.

### Pattern name(s) + why

**Boyer–Moore majority vote (candidate + cancelation).**  
Pair each non-candidate occurrence against a candidate occurrence. Because the majority count > n/2, it cannot be fully canceled — whatever survives as `candidate` at the end is the majority (when one is guaranteed).

Hash map (count frequencies, return the one with count > n/2) is correct but uses O(n) space; voting is the interview flex for O(1) space.

### Approach skeleton

1. `candidate = none`, `count = 0`.
2. For each `x` in `nums`:
   - If `count == 0`: set `candidate = x`, `count = 1`.
   - Else if `x == candidate`: `count += 1`.
   - Else: `count -= 1` (cancel one vote).
3. Return `candidate`.  
   *(If the problem did **not** guarantee a majority: second pass counting `candidate` and check `> n/2`.)*

### Concrete example (state changing)

Input: `nums = [7, 0, 0, 1, 7, 7, 2, 7, 7]`

| Step | `x` | `count` before | Action | `candidate` after | `count` after |
|------|-----|----------------|--------|-------------------|---------------|
| 1 | 7 | 0 | adopt | 7 | 1 |
| 2 | 0 | 1 | cancel | 7 | 0 |
| 3 | 0 | 0 | adopt | 0 | 1 |
| 4 | 1 | 1 | cancel | 0 | 0 |
| 5 | 7 | 0 | adopt | 7 | 1 |
| 6 | 7 | 1 | same | 7 | 2 |
| 7 | 2 | 2 | cancel | 7 | 1 |
| 8 | 7 | 1 | same | 7 | 2 |
| 9 | 7 | 2 | same | 7 | 3 |

→ **`7`**

### Common pitfalls / edge cases

1. **Skipping the `count == 0` adopt** — you must pick a new candidate when the vote empties.
2. **Returning without understanding the guarantee** — if majority isn’t guaranteed, voting alone can lie; always verify when unsure.
3. **Floor vs strict** — majority is **`> n/2`**, not `≥ n/2` (for even n, `n/2` is not enough).
4. **Sorting + pick middle** — O(n log n) correct under the guarantee (median is majority) but slower; know it as a fallback story.
5. **Init `candidate = nums[0]` with `count = 0` then loop from 0** — fine if you treat first iteration as adopt; don’t double-count carelessly.

### Complexity

- **Time:** O(n)  
- **Space:** O(1)

### Quiz cards

**Front 1:** In one sentence, why can’t a non-majority element survive Boyer–Moore when a true majority exists?  
**Back 1:** Every cancelation removes one majority and one non-majority vote (or two non-majority). Majority has more than half the seats, so it can’t be wiped out.

**Front 2:** Prompt changes to “element appearing more than n/3 times — there may be up to two.” Pattern change?  
**Back 2:** Track **two** candidates and two counts; on a third distinct value, decrement both. Then verify each with a counting pass.

**Front 3 (variant):** No majority guaranteed. What do you add after the vote loop?  
**Back 3:** One O(n) recount of `candidate`; return it only if count > n/2, else “none.”

## 3. `rearrange-elements-by-sign`

### What it’s asking

`nums` has **even length** and an **equal** number of positives and negatives. Build a new array that:

1. Starts with a **positive**
2. Alternates signs: `+, −, +, −, …`
3. Preserves **relative order** among positives and among negatives

Example: `[2, 4, 5, -1, -3, -4]` → `[2, -1, 4, -3, 5, -4]`

### Tip-offs / how you’d recognize this

- “Alternate signs” / “positive then negative” / “equal count of + and −.”
- **Stable** within each sign class (order preserved).
- Output positions for positives are even indices `0, 2, 4, …`; negatives odd `1, 3, 5, …`.
- Contrast tip-offs:
  - Unequal counts / leftover signs → two-list collect then merge with a remainder rule.
  - In-place only + no extra array → harder; often still collect or careful swaps.

### Pattern name(s) + why

**Two write pointers into fixed parity slots (even/odd index fill).**  
One pointer (`pos`) walks even indices for positives; one (`neg`) walks odd indices for negatives. Single read pass over `nums` places each value into the next free slot of its sign. Relative order falls out because you place in encounter order.

Collecting two queues then interleaving is the same idea with clearer separation — same complexity, slightly more memory bookkeeping.

### Approach skeleton

1. Allocate `result` of length `n`.
2. `pos = 0`, `neg = 1`.
3. For each `x` in `nums`:
   - If `x > 0`: `result[pos] = x`, `pos += 2`.
   - Else: `result[neg] = x`, `neg += 2`.  
     *(Problem assumes no zeros; confirm if zeros appear.)*
4. Return `result`.

### Concrete example (state changing)

Input: `nums = [2, 4, 5, -1, -3, -4]`, `n = 6`  
Start: `result = [_, _, _, _, _, _]`, `pos = 0`, `neg = 1`

| Step | `x` | Sign | Write index | `result` after | `pos` | `neg` |
|------|-----|------|-------------|----------------|-------|-------|
| 1 | 2 | + | 0 | `[2, _, _, _, _, _]` | 2 | 1 |
| 2 | 4 | + | 2 | `[2, _, 4, _, _, _]` | 4 | 1 |
| 3 | 5 | + | 4 | `[2, _, 4, _, 5, _]` | 6 | 1 |
| 4 | −1 | − | 1 | `[2, -1, 4, _, 5, _]` | 6 | 3 |
| 5 | −3 | − | 3 | `[2, -1, 4, -3, 5, _]` | 6 | 5 |
| 6 | −4 | − | 5 | `[2, -1, 4, -3, 5, -4]` | 6 | 7 |

→ **`[2, -1, 4, -3, 5, -4]`**

### Common pitfalls / edge cases

1. **Starting negatives at index 0** — prompt wants positive first; swap the initial `pos`/`neg` if the variant asks for negative-first.
2. **Treating `0` as positive** — `> 0` vs `≥ 0`; this problem’s statement uses positives/negatives only.
3. **Two-list approach forgetting stability** — append in encounter order, then `result[i] = pos[i//2]` / `neg[i//2]` by parity.
4. **Unequal counts** (variant) — after the shorter side runs out, append the rest of the longer side; don’t keep `+= 2` forever.
5. **Trying hard in-place with swaps** — easy to break relative order; prefer the O(n) extra array unless forced.

### Complexity

- **Time:** O(n)  
- **Space:** O(n) for `result` (required output; input usually treated as read-only)

### Quiz cards

**Front 1:** Why do `pos += 2` / `neg += 2` automatically alternate signs?  
**Back 1:** Evens are reserved for `+`, odds for `−`. Filling those slots in order *is* the alternate pattern, and encounter order keeps each class stable.

**Front 2:** Variant: “Begin with a negative.” What two numbers change in the skeleton?  
**Back 2:** Init `neg = 0`, `pos = 1` (swap the starting parities).

**Front 3 (variant):** Positives and negatives unequal; still alternate as long as possible, then append leftovers. Pattern tweak?  
**Back 3:** Collect two lists (or keep counts). Interleave while both nonempty; then extend with the remaining list. Same “merge two stable streams” idea.
